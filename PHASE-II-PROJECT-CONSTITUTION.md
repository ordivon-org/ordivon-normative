# Ordivon Normative Phase II Project Constitution

Status: **CURRENT PROJECT-GOVERNANCE CANDIDATE — subject to owner publication**.

Phase I established the Ordivon Normative owner boundary, Formal Core Reference Contract v1, frozen counterexample/regression families, Game and Harness/Agent semantic dogfood, a disposable conformance witness, and source-fenced owner publication. Phase II changes the project operating mode.

Phase II is **falsifier-driven deepening**, not sequential foundation expansion.

## 1. Stable project identity

Ordivon Normative remains the semantic owner of context-relative constitutive/normative admission, applicability, consequence, competence/power, and valid transformation semantics.

Its current formal core remains `FORMAL-CORE-REFERENCE-CONTRACT.md`.

Phase II does not redefine that referent and does not create a numbered Foundation series.

## 2. Anti-momentum rule

No new theory programme is opened merely because the previous programme completed, the project is active, a topic is philosophically interesting, or a cleaner ontology could be designed.

There is no default `N13 -> N14 -> N15` progression.

A new semantic programme requires a **named pressure source** and an admission decision under the Pressure-to-Programme Protocol.

If no qualifying pressure exists, the correct project state is:

`FORMAL_CORE_FROZEN / FRONTIER_OPEN / NO_ACTIVE_THEORY_PROGRAMME`.

Research inactivity under those conditions is healthy closure, not project abandonment.

## 3. Project lifecycle states

The project uses the following semantic-research lifecycle:

1. **FROZEN_CORE** — current formal contract stands; no qualifying counterexample is open.
2. **PRESSURE_OBSERVED** — a concrete downstream/domain/formal case appears to stress the contract.
3. **PRESSURE_CLASSIFIED** — the case is classified as VocabularyExtension, ModelPressure, BridgePressure, CoreFailureCandidate, or EngineeringPressure.
4. **ADMISSION_STUDY** — only CoreFailureCandidate or sufficiently repeated/irreducible BridgePressure may justify a bounded semantic investigation.
5. **ACTIVE_BOUNDED_PROGRAMME** — explicit question, counterexamples, rival hypotheses/models, stop conditions, and owner boundary are frozen before investigation.
6. **CLOSEOUT** — result is ESTABLISHED / REJECTED / DERIVED-BRIDGE / OPEN-UNDERDETERMINED / NO-CHANGE.
7. **REPUBLICATION** — owner authority advances only if current semantic owner truth materially changes.
8. **RETURN_TO_FROZEN_CORE** — default after closeout.

Engineering work, conformance-backend work, and domain adapter work have separate lifecycles and do not automatically enter states 4–7.

## 4. Formal-core reopen conditions

Formal Core v1 may be reopened only when at least one of the following is demonstrated:

- a concrete required normative distinction cannot be expressed without violating an existing core separation;
- two cases with different required normative outcomes are observationally collapsed by the current core;
- a current core obligation blocks a coherent domain case and is shown unnecessarily strong;
- repeated independent domain pressures reveal the same missing owner-general truth condition;
- a cross-owner bridge cannot be represented without either shadow-authority or owner-boundary violation.

The following do **not** reopen the formal core:

- new domain nouns or status names;
- API/schema ergonomics;
- a desire for a canonical claim grammar;
- implementation performance;
- storage/query convenience;
- one backend becoming awkward;
- one domain preferring a different representation;
- current product code lacking instrumentation;
- a consumer requesting a boolean answer.

## 5. Research-programme admission contract

Any Phase II semantic programme must state before substantive investigation:

- exact semantic question;
- named pressure/counterexample source;
- current contract clause under pressure;
- owner boundary and external owners involved;
- at least one frozen discriminator/counterexample;
- at least two materially different hypotheses when selection is at issue;
- admission burden for any new primitive/relation/category;
- explicit non-goals;
- stop/closeout conditions;
- reopen/rollback effect on Formal Core v1.

A programme that cannot state these remains exploratory notes, not an admitted semantic programme.

## 6. Primitive-admission burden

A new owner-general primitive/relation/category is admitted only if a frozen case cannot preserve a required observable distinction through the existing typed-claim/support/standing machinery or an equivalent model-plural interpretation.

`UsefulName != GeneralPrimitive`.

`RepeatedDomainObject != OnticPrimitive`.

`ConvenientStorageEntity != SemanticPrimitive`.

A new primitive must survive counterexamples and at least one alternative representation family before owner publication.

## 7. Consumer contract

Downstream owners may consume stable semantic roles, not a mandatory API/schema.

Stable consumer-facing truth roles include:

- external premise vs normative assessment;
- signed standing and explicit unknown/conflict;
- support-path identity and standing sufficiency;
- source standing/effectivity vs applicability vs path disqualification;
- context-relative Permission/Obligation/Prohibition/Status when relevant;
- change-relative Power and predecessor-relative ValidChange;
- temporal/historical standing and source/effect lifecycle separation;
- receiving-context support for jurisdiction/recognition/translation.

Consumers remain responsible for their domain content, operational state, physical facts, and owner-local semantics.

No consumer is required to call a Normative service or adopt the conformance-witness interchange representation.

## 8. Engineering admission gate

Engineering is admitted in layers:

### E0 — semantic documents only

Always permitted as owner research materialization.

### E1 — disposable conformance/falsification witness

Currently admitted. Must remain non-authoritative, non-production, current-cut-external, and easy to replace.

### E2 — domain adapter / compiler

Not globally admitted. A bounded adapter may be studied only when a concrete consumer needs a repeatable mapping from its owner-native semantics into explicit Normative fixture/claim/support inputs. It may not become domain truth owner.

### E3 — shared reference inference component

Not admitted. Requires new evidence that multiple consumers need one reusable executable semantic layer and that representation/logic choices can be stabilized without shadow authority.

### E4 — production authority / policy / enforcement service

Explicitly **NOT ADMITTED**. Requires a separate future admission study covering currentness authority, writes, safety, failure semantics, auditability, operational composition, and owner-boundary risk.

Advancement at one engineering level does not imply admission of the next.

## 9. Authority and publication discipline

Owner semantic truth lives in the owner corpus and immutable source-fenced authority publications.

Host Tasks are continuity/research-working claims. Atlas is generated currentness/history/recovery projection. Git transport commits and conformance tooling do not mint semantic authority.

A Phase II research or roadmap change advances AuthorityVersionRef only when it materially changes current owner semantic/project-governance truth. Tooling, tests, formatting, navigation-only edits, and transport synchronization do not.

## 10. Closure principle

The preferred Phase II posture is:

**Freeze the core; keep the frontier open; deepen only under falsifying pressure.**

Project quality is measured by preserved distinctions, explanatory compression, counterexample survival, owner-boundary integrity, and recoverable history — not by number of programmes, Foundations, files, APIs, or commits.
