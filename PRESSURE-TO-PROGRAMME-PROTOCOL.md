# Pressure-to-Programme Protocol

Purpose: convert downstream/domain anomalies into the **smallest correct kind of work** without reflexively reopening Ordivon Normative theory.

## 1. Record the pressure before interpreting it

A pressure record should identify:

- source owner/domain;
- concrete case/event/query;
- relevant context(s) and cut/currentness assumptions;
- observed/required distinction;
- current Formal Core clause used;
- why the current mapping is considered inadequate or awkward;
- exact evidence/provenance.

Do not begin by proposing a new primitive.

## 2. Classify the pressure

### VocabularyExtension

The current Formal Core can express the case after adding owner/domain-specific typed claim terms.

Example: `ChampionStatus`, `TournamentSeedPrivilege`, or `SettlementEntitlement`.

**Disposition:** owner/domain bridge or adapter work. No Formal Core reopen.

### ModelPressure

The semantic distinction is expressible, but one representation/backend/model becomes awkward, duplicative, or difficult to query.

**Disposition:** representation/conformance/engineering research. Core remains frozen unless multiple materially different models fail on the same distinction.

### BridgePressure

Two owners/contexts need a stable relation or translation and the difficulty is ownership/admission/provenance across the boundary rather than the local semantics themselves.

**Disposition:** bounded cross-owner bridge research. Reopen Formal Core only if every owner-correct bridge representation violates an existing core separation.

### CoreFailureCandidate

A required normative distinction cannot be expressed under the current Formal Core, or two normatively different cases collapse to the same current observable structure.

**Disposition:** formal admission study. No core mutation before frozen discriminator/counterexample and rival hypotheses exist.

### EngineeringPressure

The problem is execution, instrumentation, storage, performance, schema, product lifecycle, UX, operational safety, or missing consumer integration while semantic truth is already expressible.

**Disposition:** engineering-consumption task. No Normative semantic programme.

### OwnerBoundaryConflict

Two owners appear to claim the same truth role, or a proposed mapping requires one owner to redefine another owner's facts/semantic authority.

**Disposition:** boundary/Research-System consolidation before theory. Do not solve ownership conflict by adding a Normative primitive.

## 3. Admission matrix

| Classification | New Normative theory? | New owner bridge? | Engineering work? | Authority publication? |
|---|---:|---:|---:|---:|
| VocabularyExtension | No | Maybe | Maybe | Only if current owner semantic corpus materially changes |
| ModelPressure | Normally no | No | Often | Normally no |
| BridgePressure | Maybe, only if irreducible | Yes | Maybe | After bounded semantic bridge result if owner truth changes |
| CoreFailureCandidate | Admission study first | Maybe | No workaround as theory substitute | Yes only after successful semantic closeout |
| EngineeringPressure | No | Maybe adapter | Yes | No for tooling-only changes |
| OwnerBoundaryConflict | Not yet | Boundary work first | No | After owner-boundary resolution if truth changes |

## 4. CoreFailure admission study

A CoreFailureCandidate is promoted to an active semantic programme only after:

1. the concrete case is frozen;
2. the required distinction/outcome is explicit;
3. the current core failure is demonstrated without relying on one implementation representation;
4. at least two candidate repairs or one repair plus a strong null hypothesis are frozen;
5. the minimality burden for any new primitive is stated;
6. downstream urgency is separated from semantic truth.

If the case can be repaired by VocabularyExtension, BridgePressure resolution, or representation change, CoreFailure admission fails.

## 5. Research closeout outcomes

Every admitted semantic programme must close as one of:

- `CORE_REPAIR_ADMITTED` — owner-general semantic contract changes;
- `NO_CORE_CHANGE` — pressure resolved without Formal Core change;
- `DERIVED_BRIDGE_RESULT` — valuable cross-owner relation, no new owner-general primitive;
- `REPRESENTATION_RESULT` — implementation/model finding only;
- `OPEN_UNDERDETERMINED` — reality/question remains open, no justified owner change;
- `CANDIDATE_REJECTED` — proposed primitive/model/owner expansion failed.

History is retained; rejection is not deletion.

## 6. Publication rule

AuthorityVersionRef advances only when the owner-native semantic/project-governance truth materially changes.

It does not advance for:

- a failed pressure candidate;
- a tooling/conformance backend commit;
- a consumer implementation fix;
- generated Atlas refresh;
- transport synchronization;
- formatting/navigation-only changes.

## 7. Anti-shadow-authority checks

Before closeout, ask:

- Did storage/latest bytes become authority by convenience?
- Did an operational allow/deny result become normative Permission/Prohibition?
- Did capability/control become Power?
- Did source-context truth self-import into a receiving context?
- Did evidence/support automatically become standing?
- Did a model-specific object get promoted to semantic primitive?
- Did project momentum substitute for a counterexample?

Any `yes` blocks semantic admission until repaired.
